# Backuply

Фоновый сервис синхронизации папок на Go с локальным SQLite-индексом.
Работает между разрешёнными устройствами напрямую по TCP/TLS 1.3, в том числе
в локальной сети без интернета. Центральный сервер не требуется.

**Этап 1: рабочий Linux-прототип с одним источником изменений на папку.**
Компьютер может раздавать одну папку и принимать другую. Полученные данные можно
раздавать дальше разрешённым peers. Для одной папки пока задаётся один upstream;
одновременные изменения на нескольких устройствах ещё не поддерживаются.

Реализованы постоянная идентичность устройства, взаимная проверка сертификатов,
ACL папок, периодическое сканирование, передача недостающих блоков по 256 KiB,
проверка SHA-256, атомарная замена файлов, повторное подключение и локальный статус.
Неизменённое содержимое повторно не скачивается; индекс пока передаётся целиком.

## Сборка и тесты

Нужен Go 1.26; CI и Docker используют Go 1.26.8. Runtime не требует Python,
PostgreSQL, CGO или установленного SQLite.

```sh
go build -trimpath -o bin/backuply ./cmd/backuply
go test -race ./...
bash scripts/e2e.sh "$PWD/bin/backuply"
```

Без установленного Go можно использовать контейнер разработки:

```sh
mkdir -p .cache/go
docker compose -f compose.dev.yaml run --rm dev go build -trimpath -o bin/backuply ./cmd/backuply
docker compose -f compose.dev.yaml run --rm dev go test -race ./...
docker compose -f compose.dev.yaml run --rm dev bash scripts/e2e.sh /workspace/bin/backuply
```

По умолчанию контейнер разработки работает с UID/GID 1000. При необходимости
задайте `BACKUPLY_UID` и `BACKUPLY_GID` своего пользователя.

## Два устройства

На каждом устройстве сначала создайте идентичность в отдельном каталоге состояния
и обменяйтесь напечатанными Device ID по доверенному каналу:

```sh
bin/backuply init -state-dir /absolute/path/to/backuply-state
```

Device ID — 64 шестнадцатеричных символа SHA-256 сертификата. Закрытый ключ
`key.pem` остаётся на своём устройстве; обменивать или копировать его не нужно.

Конфигурация сервера-источника, например `server.conf`:

```ini
[service]
listen = 192.168.1.10:24800
state_dir = /absolute/server/backuply-state
scan_interval = 5s

[peer "laptop"]
address = 192.168.1.20:24800
device_id = REPLACE_WITH_LAPTOP_DEVICE_ID

[folder "projects"]
path = /absolute/server/projects
source = local
peers = laptop
```

Конфигурация ноутбука `laptop.conf`:

```ini
[service]
listen = 192.168.1.20:24800
state_dir = /absolute/laptop/backuply-state
scan_interval = 5s

[peer "server"]
address = 192.168.1.10:24800
device_id = REPLACE_WITH_SERVER_DEVICE_ID

[folder "projects"]
path = /absolute/laptop/projects
source = server
peers = server
```

Подставьте реальные пути, адреса и ID. Каталог `state_dir` должен совпадать с
использованным при генерации идентичности. Folder ID (`projects`) одинаков на обоих
устройствах, локальные пути могут различаться. Приёмник лучше начать с пустой папки:
отличающееся существующее содержимое сервис откажется перезаписывать.

На каждой машине, с её собственным конфигом:

```sh
bin/backuply check -config server.conf
bin/backuply init -config server.conf
bin/backuply run -config server.conf
```

`init -config` создаёт отсутствующие папки и marker `.backuply-folder` с Folder ID.
Это явное подключение папки; обычный запуск не восстанавливает потерянный marker.
Повторный `init` при остановленном сервисе сохраняет идентичность и проверяет marker.
Потерянный marker сначала расследуйте: так может выглядеть отключённый диск.

`run` остаётся на переднем плане для systemd/Docker. Для проверки из другого терминала:

```sh
bin/backuply status -config server.conf
```

Статус содержит ошибки папок, время последней успешной сверки и счётчики байтов
за текущий запуск. Запрос идёт через приватный Unix-сокет в `state_dir`.
После изменения конфигурации сервис нужно перезапустить. Остановка — SIGTERM
или Ctrl+C. Два процесса не могут одновременно использовать один `state_dir`.

## Фоновый сервис и Docker

[Инструкция systemd](docs/service.md) описывает установку под отдельным пользователем,
права на рабочие папки и автозапуск. Готовый unit: [backuply.service](deploy/systemd/backuply.service).

Для проверки контейнера без подключения рабочих папок:

```sh
docker compose build
docker compose run --rm backuply init -config /etc/backuply/backuply.conf
docker compose up --wait --wait-timeout 60
docker compose exec backuply /usr/local/bin/backuply status -config /etc/backuply/backuply.conf
docker compose logs -f backuply
docker compose down
```

Включённый Compose конфиг содержит пустой узел, а порт опубликован на localhost. Для LAN добавьте
папки через bind mounts, peer/folder секции и замените адрес публикации на IP LAN.
Runtime использует UID/GID 10001: папки должны быть доступны этому пользователю.
Идентичность и индекс сохраняются в named volume `state` при `compose down`.
Healthcheck подтверждает, что демон отвечает; ошибки отдельных папок видны в статусе.

## Ограничения первого этапа

- Удаления на источнике пока не удаляют файлы у получателей. Переименование оставит
  старую копию на получателе. Изменение типа файл/каталог требует ручного решения.
- Локальная правка или удаление индексированного файла/каталога получателя
  приостанавливает синхронизацию всей этой папки. Другие папки продолжают работу.
  Автоматического слияния и команды принудительного разрешения пока нет.
- Получаемую папку не следует редактировать одновременно с синхронизацией.
  Проверки обнаруживают изменения до замены, но не дают транзакционной гарантии
  против стороннего приложения, записывающего в последний момент перед rename.
- Поддерживаются обычные файлы и каталоги. Symlinks и специальные файлы останавливают
  сканирование. Нет правил исключений, сохранения mtime, xattrs, ACL и hardlink-связей;
  точные права каталогов не синхронизируются, создаваемые каталоги сохраняют owner rwx.
- Передаются фиксированные блоки, поэтому вставка в начало может потребовать
  значительной передачи. FastCDC, batching мелких файлов, pipeline, watchers,
  локальное обнаружение и SSH запланированы следующими этапами.
- После обрыва целый незавершённый файл собирается заново; уже применённые файлы
  переиспользуются. После SIGKILL могут остаться `.backuply-tmp-*`: их можно удалить
  при остановленном сервисе. Истории, квоты временных данных и on-demand пока нет.
- Стартовые лимиты: 8 GiB на файл, 100 000 записей и 64 MiB метаданных на папку,
  32 peers и 128 папок в конфиге. Это ограничения прототипа, не показатели скорости.
