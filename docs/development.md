# Разработка и критерии готовности

Архитектура обоснована в [architecture.md](architecture.md). Выбран собственный
движок на Go + SQLite. Реализован первый этап; остальные этапы ниже — план,
а не скрытые возможности текущего бинарника.

## Что работает сейчас

- Go-демон с INI-конфигурацией, постоянными Ed25519-сертификатами, TLS pinning,
  SQLite WAL, ACL папок и private Unix socket для статуса.
- Периодический scanner и передача недостающих фиксированных блоков 256 KiB;
  SHA-256, проверка локальных изменений, fsync и атомарный rename.
- Docker multi-stage build создаёт статический бинарник в scratch с UID 10001.
  Compose сохраняет identity/index в volume, публикует порт только на localhost.
- GitHub Actions на push/PR/manual проверяет форматирование, зависимости, `go vet`,
  unit/integration tests с race detector и тест двух отдельных процессов.
  Второй job собирает контейнер, инициализирует identity и проверяет ответ демона.
- Unit systemd для фонового запуска и инструкция администратора в [service.md](service.md).

Команды из корня репозитория:

```sh
docker compose config --quiet
docker compose build
docker compose run --rm backuply init -config /etc/backuply/backuply.conf
docker compose up --wait --wait-timeout 60
docker compose logs --no-color
docker compose down
```

Для другого локального порта:

```sh
BACKUPLY_PORT=24801 docker compose up --wait --wait-timeout 60
```

Docker smoke проверяет запуск демона с пустым конфигом и статус; функциональный
перенос файлов отдельно проверяется в Go integration tests и `scripts/e2e.sh`.
Скрипт создаёт временные папки и identity, запускает два процесса, проверяет
первичную передачу, офлайн-изменение, перезапуск и сохранение идентичности.

```sh
mkdir -p .cache/go
docker compose -f compose.dev.yaml run --rm dev go test -race ./...
docker compose -f compose.dev.yaml run --rm dev go vet ./...
docker compose -f compose.dev.yaml run --rm dev go build -o bin/backuply ./cmd/backuply
docker compose -f compose.dev.yaml run --rm dev bash scripts/e2e.sh /workspace/bin/backuply
```

Go-зависимости зафиксированы в `go.mod` и `go.sum`, toolchain сборки — 1.26.8.
Для первой загрузки образа и модулей нужна сеть; runtime работает в LAN без неё.
Сами GitHub Actions должны запускаться в GitHub после отправки изменений;
локальные проверки не являются удалённым запуском workflow.

Проверено локально 8 сентября 2026: `go mod verify`, `go vet`, все Go-тесты с
race detector, двухпроцессный E2E, Docker build и healthcheck. В E2E после
офлайн-изменения одного байта в файле 1 MiB получатель после рестарта скачал
256 KiB и переиспользовал 768 KiB. Это функциональный пример, не бенчмарк скорости.
Тестовые процессы, контейнер, сеть и отдельный тестовый том удалены.
Unit systemd подготовлен, но системная установка и запуск на этой машине не
выполнялись: проверка `systemd-analyze` сообщает об отсутствующем установленном
`/usr/local/bin/backuply`. Инструкции установки приведены в `service.md`.

## Этапы

### 0. Выбор движка — завершён

Пользователь выбрал Go + SQLite и отдельный фоновый сервис с файлом конфигурации.
Syncthing остаётся внешним эталоном для будущих бенчмарков, не зависимостью runtime.

### 1. Вертикальный прототип Go — реализован

Реализованы `go.mod`/`go.sum`, CLI и daemon, постоянная идентичность, folder ACL,
SQLite-index и scanner. Подключение по явному адресу, TCP/TLS с pinning,
фиксированные блоки, проверка хешей и атомарное применение. Один явно выбранный
writer на папку задаётся `source`. Это ещё не multi-master. Управляющие сообщения
v1 имеют length-prefixed JSON формат, блоки передаются отдельно бинарными кадрами;
Protobuf и несколько запросов в полёте отложены до этапа оптимизации.

Критерии: два отдельных процесса сходятся по байтам файлов, повторная сверка
не скачивает неизменённое содержимое, неизвестный peer не получает индекс,
недоступная папка не выдаёт блоки, повреждение/обрыв не публикует частичный файл.
mtime, точные права каталогов и другие расширенные метаданные пока не сохраняются.

### 2. Причинность и восстановление — следующий этап

Специфицировать и реализовать version vectors, tombstones, конфликтующие ревизии,
checkpoint/epoch, журнал применения и идемпотентное воспроизведение событий.
Добавить периодический аудит и защиту отсутствующего корня.

Готово, когда три узла после офлайн-правок и всех порядков доставки сходятся,
конкурентные данные сохранены, delete/edit виден как конфликт, старый отключённый
peer не воскрешает удалённое молча. Crash между записью, fsync, rename, commit и
ACK восстанавливается с корректными файлами и индексом.

### 3. Эффективная LAN-синхронизация — запланировано

Добавить watcher, локальное обнаружение, ограниченный параллелизм, batching,
cursor-based индекс, FastCDC, кэш с квотой, resume и выбор источника блока.

Готово, когда вставка в начало большого несжатого тестового файла сохраняет
повторное использование большей части неизменённых данных, память ограничена
при медленном получателе, небольшие файлы не требуют отдельной сессии, а отключение
выхода в интернет не мешает обнаружению и синхронизации в разрешённом сегменте.
Порог выигрыша CDC фиксировать после сравнения CPU/диска/трафика с baseline.

### 4. SSH и эксплуатация — запланировано

Добавить SSH-адаптер, known_hosts, ключи/ssh-agent, transport policy и reconnect.
Конфигурация и локальный API показывают состояние peers, отставание, конфликты,
причину остановки папки, очередь и потребление ресурсов.

Готово, когда `ssh-only` работает при закрытом внешнем P2P-порту и не открывает
прямых соединений, неверный host key отклоняется, обрыв SSH возобновляется,
а переключение транспорта сохраняет те же ревизии и правила конфликтов.

### 5. Desktop и место — запланировано

Проверить native-агенты Windows/macOS, правила имён/регистра, обработку открытых
файлов и автозапуск. Добавить выборочную синхронизацию и квоты истории.
On-demand/placeholder режим — отдельный этап со своим RFC, включая offline-open,
pin/unpin, доступность держателей данных и защиту последней копии.

Оценивать календарные сроки после проверки модели multi-master и crash recovery.
Переносимость файловой семантики — отдельная часть работы.

## Целевая структура собственного движка

Целевая структура; в этапе 1 chunking, scanner и apply объединены в `internal/store`,
а управление — в `internal/daemon`. Отдельные discovery/sync/api пакеты ещё впереди:

```text
cmd/backuply/          CLI и запуск демона
internal/config/      настройки, миграции конфигурации
internal/identity/    ключи устройств и доверие
internal/scanner/     обход, watcher, rescan, ignore
internal/index/       SQLite, версии, курсоры и миграции
internal/chunker/     fixed-size и CDC, хеширование
internal/sync/        планирование, конфликты, tombstones
internal/store/       блоки, временные файлы, квоты
internal/apply/       запись и восстановление после сбоя
internal/protocol/    framing, capabilities, ограничения
internal/transport/   TCP/TLS и SSH
internal/discovery/   LAN и статические адреса
internal/api/         локальное управление
proto/                схемы сообщений
test/integration/     несколько процессов/узлов
test/bench/           генераторы данных и измерения
```

## Docker и GitHub Actions для Go

Dockerfile уже использует multi-stage build, toolchain и Go-зависимости зафиксированы.
Для выпусков дополнительно закрепить base image digest и Action commit SHA.
Runtime минимальный, non-root; будущий SSH-профиль должен содержать OpenSSH
client либо использовать его на хосте. Distroless без `ssh` не выполнит subprocess
адаптер. Конфигурацию, identity и SQLite хранить в отдельном постоянном volume;
пользовательские папки — отдельные bind mounts. БД не синхронизировать между peers.

Для интеграционных тестов — три контейнера в изолированной bridge-сети,
раздельные state/data volumes и явные адреса. Для испытания discovery в реальной
LAN на Linux — отдельный профиль с host networking и ограничением интерфейсов.
Bridge-тест не доказывает, что multicast работает между физическими компьютерами.
У Docker Desktop свои особенности host networking; на ноутбуках основной способ
эксплуатации — native daemon с системным автозапуском.
[Docker host networking](https://docs.docker.com/engine/network/drivers/host/).

Будущий CI расширять вместе с кодом:

| Проверка | Когда |
| --- | --- |
| `gofmt`, `go vet`, unit/property tests модели версий | Каждый PR |
| `go test -race` на поддерживаемом Linux runner | Каждый PR |
| Native tests Linux, Windows, macOS | При добавлении соответствующих платформ |
| Fuzz smoke: framing, пути, chunker, манифесты | Каждый PR; длительный прогон по расписанию |
| Три узла: изменения, офлайн, конфликт, delete, restart, resume | Каждый PR после этапа 2 |
| Прямой TLS и SSH-only с тестовым sshd и одноразовыми ключами | После этапа 4 |
| Docker build + проверка запуска | Каждый PR, реализовано для Go-демона |
| Vulnerability scan, SBOM, native artifacts и multi-arch image | При подготовке релизов |
| Бенчмарки на стабильном выделенном стенде | По расписанию и перед релизом |

Сборка Docker в GitHub Actions следует обычному workflow сборки и проверки
контейнеров; для multi-platform и кэша добавить Buildx по мере необходимости.
[Docker: GitHub Actions](https://docs.docker.com/build/ci/github-actions/).
Hosted runners подходят для функциональных проверок, но их колебания не должны
становиться порогом «скорость упала на 5%». Измерения хранить как артефакты с
версией бинарника, датасета и параметрами машины. Текущий workflow не публикует
образы и не является release pipeline.

## Матрица проверки

Все разрушительные сценарии выполняются на генерируемых временных данных.

| Сценарий | Что проверять |
| --- | --- |
| 100 000 файлов по 1–16 KiB; отдельно дерево исходников | Файлы/с, индекс, открытые дескрипторы, batching |
| Файл 1 GiB: перезапись 4 KiB, вставка в начало/середину, append | Байты блоков и манифестов, reuse, CPU chunking |
| Полностью новый/сжатый/случайный файл | Корректная полная передача, bounded overhead |
| 1 GbE, быстрый LAN, Wi-Fi; задержки и потери | Полный трафик, CPU, fairness и p95 задержки применения |
| Повторное подключение без изменений | Нулевой payload файлов, объём служебного обмена |
| Конкурентные правки на трёх узлах, clock skew | Сходимость без зависимости от часов, сохранность конфликтов |
| Удаление + офлайн-правка, долгий offline, возвращение исключённого peer | Tombstones, checkpoint, отсутствие молчаливого воскрешения |
| Обрыв, kill, рестарт на стадиях записи и commit | Итоговый файл целый, корректный resume, согласование БД с ФС |
| ENOSPC, read-only, пропавший mount, watcher overflow | Пауза и объяснимая ошибка вместо потери данных |
| Переименование, пустые файлы/каталоги, регистр, Unicode | Верная семантика и явные неподдерживаемые случаи |
| Повреждённый блок, oversized frame, `..`, symlink race, чужой folder ID | Отклонение входа, отсутствие выхода за корень и доступа к чужим данным |
| Изменение источника при хешировании/передаче; запись на получателе | Повторная проверка версии, отсутствие тихого затирания |
| Исключения и локально несинхронизируемые папки | Исключение не распространяется как удаление |
| SSH-only при закрытых P2P-портах; неверные ключи | Соблюдение политики и правильная аутентификация |

При сравнении с rsync использовать одинаковый шифрованный канал; его направленный
режим оценивает эффективность переноса, но не доказывает multi-master семантику.
Cold/warm cache и каждый тип диска измерять отдельно. Главный release gate —
сохранность данных и сходимость, затем ограниченность ресурсов, затем скорость.
